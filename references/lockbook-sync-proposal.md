# RFC: `lockbook sync-dir` and `.lockbookignore`

## Summary

Two new features for coding workspaces, agents, and automation:

1. **`lockbook sync-dir`** — bidirectionally sync a real local directory with a Lockbook folder. Files stay on local disk; Lockbook is the sync backend.
2. **`.lockbookignore`** — a `.gitignore`-style file to exclude build artifacts, caches, and local-only files from sync.

This complements `lockbook fs` rather than replacing it. `lockbook fs` is great for "mount my Lockbook like a drive." `sync-dir` is for "keep a real local working tree in sync with Lockbook."

## Motivation

`lockbook fs` is backed by a userspace NFSv3 server. NFS is a poor fit for coding workloads:

- Git does thousands of `stat`/readdir calls — NFS makes these expensive
- `git fsmonitor` explicitly refuses to support network-mounted repos
- Build tools, LSPs, and file watchers behave poorly over network filesystems
- Files disappear when `lockbook fs` stops — you can't work offline

The Lockbook team already flagged this in their ["Multimedia Updates"](https://lockbook.net/blog/multimedia-updates/) post: they were "pausing for reflection" on whether to keep investing in NFS and noted that platform-specific alternatives may deliver a better experience.

`sync-dir` solves this by keeping files on native local disk and using Lockbook as the sync layer — the same model used by Syncthing, Unison, and most professional sync tools.

## CLI

```bash
lockbook sync-dir <lockbook-folder> <local-dir>
```

- Long-running process; files persist on disk when stopped
- On restart, re-reconciles from server state before resuming sync
- `<local-dir>` is created if it doesn't exist

Optional flags:
- `--pull-interval <duration>` — remote polling interval (default: 5s)
- `--no-watch` — fall back to periodic scans instead of inotify/FSEvents

## Sync semantics

**Startup — server wins:**

| State | Action |
|---|---|
| Remote only | Materialize locally |
| Remote + local unchanged | Apply remote |
| Remote + local both changed | Remote → canonical path, local → `file.conflict-<timestamp>` |
| Local only | Upload to Lockbook |

**While running:**
- Local changes: `inotify` (Linux) / FSEvents (macOS) → debounce → upload
- Remote changes: periodic `lockbook sync` → apply locally
- Conflict: remote wins, local copy saved as `file.conflict-<timestamp>`

**Never silently loses local bytes.** Conflicting content is always preserved as a sidecar.

## State storage

Sync state (path→file-id mapping, content hashes, baselines) is stored in **Lockbook's existing embedded database** — no separate SQLite needed. Lockbook already has a crash-safe local db (`db.local_metadata`, `db.base_metadata`, etc.); sync-dir state fits naturally alongside it, keyed by the local path being synced.

## `.lockbookignore`

Generated on first `sync-dir` run at the root of the local directory, as documentation. Built-in defaults apply with or without the file:

```gitignore
# .lockbookignore — generated by lockbook sync-dir
# Patterns below are ignored by default even without this file.
# Add your own exclusions after the defaults.

.git/
*.sqlite
*.sqlite-shm
*.sqlite-wal
node_modules/
target/
__pycache__/
.DS_Store
```

Same syntax as `.gitignore` (globs, negation with `!`, trailing `/` for directories, leading `/` anchors to sync root).

`.lockbookignore` itself is implicitly ignored — it never syncs to Lockbook.

## Implementation

Reuses existing `lb-rs` machinery for auth, file tree enumeration, content read/write, and sync. New code lives in a sync-dir module handling:
- watcher integration (inotify/FSEvents)
- reconcile engine
- `.lockbookignore` parsing (suggest reusing an existing `gitignore`-compatible crate)

## Open questions

1. Should v1 create `<lockbook-folder>` if it doesn't exist, or require it upfront?
2. `<name>.conflict-<timestamp>` or `<stem>.conflict-<timestamp>.<ext>` for conflict sidecars?
3. One-shot `--reconcile` flag for scripting use cases?
4. Eventually: push-based remote change notification instead of polling?

## Rollout

**v1:** `sync-dir` command, server-wins startup, inotify/FSEvents watcher, `.lockbookignore`, conflict sidecars, state in existing lb-rs db.

**Later:** Windows watcher, one-shot mode, nested ignore files, smarter rename tracking, desktop app integration.
